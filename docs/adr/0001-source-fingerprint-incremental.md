# 增量判定采用写入目标对象的源端指纹元数据

S3 协议不允许写入方设置对象的 LastModified：对象复制到目标端后，其 LastModified 是复制时间而非源端修改时间，直接比较两端 LastModified 会让增量判定永远命中"不同"，退化为每次全量；ETag 在分片上传时不是 MD5，且 MinIO/RustFS/AWS 实现细节有差异，也不可直接跨端比较。我们决定：复制对象时把源对象的 size + ETag + LastModified 作为源端指纹写入目标对象的用户元数据（`x-amz-meta-src-*`），后续执行以 size + 指纹元数据判定"相同"；目标对象存在但无指纹（由其它系统写入）时视为无法判定，按冲突策略处理（默认源端权威覆盖）。

## Considered Options

- **只比较 size**：最简单，但同尺寸的内容变化会漏传，迁移场景不可接受。
- **Sidecar 本地传输台账**：换机器、重装插件即失效，且台账与目标端实际状态会漂移（目标对象可能被其它系统改动或删除）。
- **源端指纹元数据（选定）**：状态随对象走，无本地依赖，任何机器上重跑都能正确增量；代价是目标对象携带额外元数据，且指纹方案成为兼容性契约。

## Consequences

- 元数据的键名与格式一经发布即成契约：更改会使已迁移对象失去指纹、下次执行按冲突全量覆盖。演进只能新增键、保留旧键读取。指纹中的修改时间存为 Unix 秒（`x-amz-meta-src-mtime`）：LIST 返回毫秒精度而 HEAD（RFC 2822）只有秒精度，字符串时间戳永远无法跨两种来源匹配——已在 RustFS 双端集成测试中验证并回归。
- 复制会覆盖目标对象原有的用户元数据吗？不会——只追加/更新 `x-amz-meta-src-*` 命名空间下的键，但 S3 的 PUT 是整对象替换，目标对象上由其它系统写入的自定义元数据在覆盖时会丢失。这是源端权威策略的已知代价。
- 用户用其它工具（mc、rclone）向目标写入的对象没有指纹，会被本插件视为冲突并按策略覆盖。
